# Milestones

Each milestone has a **done-when**: a test you can run or a number you can point at.

The thread through the project: **M2 predicts the numbers and measures the MoE baseline, M3–M4
beat it.**

---

## M0 — Foundation ✅
Walking skeleton: every later milestone plugs into it.

- `uv` environment (Python 3.12 to match Colab TPU runtimes), `scripts/check_env.py`
- `moe/data.py`: TinyStories, byte-level tokens (vocab 256; the raw file is memmapped as tokens)
- `moe/model.py`: dense decoder-only transformer in plain JAX (params pytree, pure `forward`);
  `ffn` is the seam for the MoE layer
- `moe/train.py`: AdamW + warmup-cosine + grad clipping, jitted step, val loss, tok/s
- `tests/`: ~10M param count, causality, single-batch overfit, data round-trip

**Done-when:** `uv run pytest` is green, and a TinyStories smoke run shows loss falling.
*Measured 2026-10-26:* base = 10,818,432 params, ~2.7k tok/s on the M2 CPU; tiny preset reaches
val 2.62 after 600 steps.

## M1 — MoE layer ✅
`moe_ffn` in `moe/model.py`: a Mixture-of-Experts FFN, Switch/GShard-style with einsum
dispatch/combine. Enabled when `n_experts > 0`.

- Top-k softmax router (raw probabilities as gates, so the router gets LM gradient even at k=1)
- Each sequence is a routing group with capacity `ceil(k·S·cf/E)`; first choices claim slots
  before second choices, then earlier positions first; overflow assignments are dropped
- Switch load-balancing loss (1.0 = balanced) + ST-MoE router z-loss, averaged over layers
- **Decision:** "10M" = **total** params. `moe` preset: 8 experts, top-2, d_ff 192/expert →
  10,836,864 total / 5,528,448 active (the dense `base` has the same total)
- Known caveat: with top_k > 1 and dropping, a later token can evict an earlier token's 2nd
  choice, so routing is only strictly causal when nothing is dropped (tested).

**Done-when:** ✅ tests show E=1,k=1 matches the dense FFN; the router gets gradient from the LM loss
alone; aux = 1 balanced / E collapsed; drop accounting is exact; dropped fraction is logged.
*Measured 2026-10-26 (M2 CPU, `moe` preset, 150 steps):* drop 40% → 6%, aux 1.37 → 1.07, val
2.37; ~3.0k tok/s vs dense 2.7k despite half the active params: einsum dispatch overhead
eats most of the saving. That gap is what M3–M4 target (CPU numbers are only indicative).

## M2 — Training, napkin math, baseline ⏳ (ready to run; needs the TPU)
Done locally:
- ✅ **Napkin math** (`docs/napkin_math.md`, generated by `scripts/napkin_math.py`): every op is
  memory-bound on v5e; the einsum MoE is predicted *slower* than dense (10.4 vs 8.0 ms/step);
  routing costs more than the experts; targets are ~1.4x (grouped matmul) and ~5.7x (fused) on
  the MoE layer.
- ✅ `dense_matched` preset (d_ff 384): same active params/FLOPs per token as `moe`
- ✅ Runs write `runs/<name>/{config.json, params.pkl, metrics.jsonl}`; fixed val batches;
  per-layer expert load logged; `moe/sample.py`; `scripts/plot.py` (val loss, expert load)
- ✅ `scripts/bench_moe.py`: layer-level fwd / fwd+bwd timing, with "experts only" to isolate
  routing overhead; `--profile` writes a trace. On the M2 CPU, routing is 59% of the MoE layer
  forward (predicted 59%).
- ✅ TPU runbook: `docs/tpu.md`, `uv sync --extra tpu`

On the TPU (`docs/tpu.md`):
- [ ] Baseline profile of the einsum MoE layer → the number M3–M4 must beat
- [ ] Full runs of `base`, `dense_matched`, `moe`; loss curves + expert-load plots committed

**Done-when:** MoE beats `dense_matched` on val loss (same active FLOPs), or the writeup explains
why not; the measured layer time sits next to the napkin-math prediction.

## M3 — Pallas grouped matmul
Replace einsum dispatch (which spends FLOPs and memory on one-hot/padded tensors) with tokens
sorted by expert and a **grouped matmul** kernel (megablox-style, ragged groups).

| Sub | Scope | Done-when |
|-----|-------|-----------|
| 3a | Tiled matmul: BlockSpecs, grid | matches `jnp.dot` (interpret mode, locally) |
| 3b | Grouped matmul forward | matches the M1 layer's outputs |
| 3c | Backward via `custom_vjp` | `jax.grad` matches the M1 layer; check passes |

## M4 — Fusion, benchmark, integration (TPU)
- Fuse further: activation into the GMM, then the combine/scatter. Benchmark each step on its
  own.
- Speedup table vs the M2 baseline, roofline plot, profiler traces, and measured-vs-predicted
  numbers.
- Swap the kernel into training.

**Done-when:** a measurable layer-level speedup and an end-to-end step-time improvement with an
unchanged loss curve.

⚠️ **Hardware:** the M2 Mac can't compile Pallas kernels. Interpret mode checks correctness
only, and its timings mean nothing. M2's full runs and all of M4 need a TPU: Colab TPU, Kaggle
TPU, or **TPU Research Cloud** (apply early, since approval takes time).
